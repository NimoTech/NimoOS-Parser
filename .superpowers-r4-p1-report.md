# Task P2 — optional max_pages via docling page_range

## Change

- `parser/routes/extract.py`: `ExtractRequest` gains `max_pages: Optional[int] = Field(default=None, ge=1)`.
  In the docling-native branch, when `body.max_pages is not None and ext == ".pdf"`, builds
  `page_range=(1, body.max_pages)` and passes it (plus an out-param dict) to `to_markdown`. Gated to
  `.pdf` only — see experiment below. `truncated` is now `True` if char-truncated (existing logic,
  unchanged) OR if a page cap was applied and docling's reported total page count exceeds
  `max_pages`; if the page count is for some reason unavailable, falls back to assuming truncation
  happened (documented as a pessimistic approximation in code comments).
- `parser/docling_extractor.py`: `to_markdown` gains two keyword-only params: `page_range` (forwarded
  to `self._converter.convert(source, page_range=...)` only when not `None`, so old callers with no
  `page_range` get byte-identical behavior/return type) and `page_count_out` (an optional caller-owned
  dict; if given, filled with `{"total_pages": result.input.page_count}`). Chose an out-param over
  changing the return type to `(markdown, page_count)` because `to_markdown` has other callers
  (`pipeline_text.py` ×2, `routes/test.py` ×1) outside this task's scope, and an out-param keeps their
  contract (`-> str`) untouched. Also deliberately NOT stored as an instance attribute on
  `DoclingExtractor` — it's a process-wide singleton reused across concurrent threadpool requests
  (`extract()` is `def`, not `async def`, specifically so docling runs off the event loop in FastAPI's
  threadpool), so any shared mutable state on `self` would race between concurrent requests.

## Experiment (ahead of writing code)

Built a real 5-page fixture (`tests/fixtures/extract/multi_page.pdf`, generated via python-docx
`add_page_break()` + `soffice --headless --convert-to pdf`, each page holding a unique
`"PAGE N MARKER"` string; `multi_page.docx` is the pre-conversion source, kept as a fixture too) and
ran `DocumentConverter.convert(...)` directly against the deployed venv's docling:

- **PDF, no `page_range`**: `result.document.export_to_markdown()` contains all 5 markers.
  `result.input.page_count == 5`. `len(result.document.pages) == 5`.
- **PDF, `page_range=(1, 1)`**: markdown contains only "PAGE 1 MARKER" (34 chars vs 178 full).
  `len(result.document.pages) == 1` — but `result.input.page_count` is **still 5** (it reflects the
  source's real total unconditionally, not what got converted). This is the reliable total-page-count
  source the route uses for exact `truncated` computation.
  `page_range=(1, 10)` (exceeding the actual 5 pages) does not error — converts all 5, no crash.
- **DOCX, `page_range=(1, 1)`**: returns **all 5 markers**, unchanged from the no-`page_range` call —
  silently ignored, no exception. `result.input.page_count == 0` for docx (not populated/not
  applicable — DOCX has no backend page concept before rendering; Word "page breaks" aren't exposed
  as document structure to docling's DOCX backend). This is exactly the "behaves oddly" case flagged
  in the task — forwarding `page_range` for non-PDF formats would silently do nothing while looking
  like it did something, so the ROUTE (not the extractor) gates forwarding to `ext == ".pdf"` only.
- **`.md`**: confirmed via existing code path (and pinned by the pre-existing
  `test_extract_plain_markdown_file_still_200` test) — plain-read branch never imports or calls
  docling at all, so this is a non-issue for `.md`/`.txt`/other plain-read extensions; `max_pages` is
  simply ignored for them (never reaches the docling branch's gate check).
